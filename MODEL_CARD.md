#### Description

`ibm-research/MoLFormer-XL-both-10pct` is IBM Research's chemical language model MoLFormer-XL (Ross et al., arXiv:2106.09553), pinned here to revision `361063d0ad524ef77cf39b08469f6be770dc550f`. It is a transformer encoder trained with a masked-token objective on molecules written as **SMILES strings**; the upstream card describes pretraining on molecules from PubChem and ZINC, and this checkpoint is the variant trained on a 10 % sample of both. The pinned `config.json` names 12 hidden layers, hidden size 768, 12 attention heads, intermediate size 768, rotary position embeddings, a 2,362-token vocabulary and `max_position_embeddings` 202; the base encoder holds 44,375,040 parameters and the sequence-classification model 45,557,762 with its newly initialised head. Its distinguishing choice is **linear attention with random feature maps** rather than quadratic attention, which is what let it scale to a billion-molecule corpus — and which has a consequence for reproducibility recorded below. At inference the model returns a contextual 768-dimensional hidden state per token; it produces a representation, not a property prediction, and it is adapted by gradient training rather than by in-context conditioning.

What this repository adds is the `MolformerPipeline` class in `src/molformer_chemistry_pipeline/pipeline.py`: manifest verification of the 7-file snapshot — **including the two Python files the loader executes** — before any model library is imported (`verify_snapshot`, which refuses a manifest that omits them), fresh-clone staging at the pinned revision only (`stage_missing_files`), a loader that reads the verified directory with `local_files_only=True` and loads the tokenizer *without* remote code, syntactic SMILES validation with named ceilings (`check_smiles_syntax`, `validate_inputs`), mean-pooled molecule embeddings (`embed`), bounded gradient fine-tuning of a `MolformerForSequenceClassification` head plus the last *n* encoder layers (`adapt`), held-out classification metrics (`evaluate`), argmax classification with per-class scores (`classify`), and a safetensors adapter artifact that carries the linear-attention feature buffers as serving state and is digest-verified before deserialization (`save_artifact`, `from_artifact`).

Two upstream properties shape the package and are stated rather than hidden. **The pinned code needs a newer Transformers than DIMER's standard:** it calls `transformers.masking_utils.create_bidirectional_mask(inputs_embeds=...)`, which exists only in Transformers 5.5.0 and later, so this repository pins `transformers==5.17.0` instead of 4.57.6. **Inference is stochastic under upstream's defaults:** `config.json` ships `deterministic_eval: false`, which makes the linear-attention random features be redrawn on *every* forward pass, so two identical calls return different embeddings (measured on the pinned checkpoint: a pooled vector's mean moved from −0.00137 to −0.00234 between consecutive calls). This package loads with `deterministic_eval=True`, which uses the feature weights the checkpoint itself stores, and exports those buffers with any adapter.

#### Intended Use and Limitations

###### Primary Intended Uses

Two tasks are exposed. **Molecule representation:** input is 1 to `MAX_MOLECULES_PER_CALL = 64` molecules as SMILES strings of at most `MAX_TOKENS = 200` tokens; output is one 768-dimensional vector per molecule (the mean of the last hidden state over non-padding tokens), suitable as features for a downstream model, for similarity search across a compound set, or for clustering. **Molecular-property classification:** given a labelled dataset of `{id, smiles, label}` records with 2 to 20 classes, the pipeline fine-tunes a classification head (optionally with the last encoder layers) and then predicts a class with per-class scores for new molecules. Envisioned application domains are cheminformatics workflows where a modest labelled set exists — flagging compounds by a measured binary property, triaging a virtual library before more expensive computation or assay, transferring a property model within a chemical series, and teaching or evaluating chemical-language-model transfer. In a larger system the pipeline is a feature extractor and a fine-tuning baseline whose output feeds a chemist's review or a downstream model, not an autonomous screening service.

###### Primary Intended Users

Intended users are cheminformaticians, computational chemists and machine-learning engineers working with molecular data, in research or in-house enterprise use. The pipeline assumes its users understand that a pretrained chemical language model encodes SMILES statistics rather than validated chemistry; that analogues in one chemical series share a scaffold, so a random split leaks and inflates every metric (scaffold or cluster splitting is their responsibility — the pipeline cannot detect series structure); that this repository validates SMILES **syntactically only** and ships no cheminformatics toolkit, so a chemically impossible string will be embedded without complaint; that the drug-like PubChem/ZINC pretraining distribution leaves inorganics, organometallics and polymers out of distribution with no error to say so; that the softmax scores are uncalibrated; and that running the default path **executes third-party Python** in their environment.

###### Out-of-scope use cases

1. **Capability boundary:** the pipeline exposes whole-molecule embeddings and whole-molecule classification only. It does not perform regression on continuous properties, molecule generation or optimisation, reaction prediction, retrosynthesis, 3D conformer or descriptor computation, substructure search, or any of the published MoleculeNet benchmarks; it does not compute chemical validity, and it does not load the other MoLFormer checkpoints.
2. **Input boundary:** SMILES must be non-empty strings without surrounding whitespace, drawn from the accepted character set, with balanced parentheses and brackets and paired ring-closure digits, tokenizing to at most 200 tokens (the checkpoint's 202 position embeddings minus `<bos>`/`<eos>`). A longer molecule is **refused, not truncated** — a truncated SMILES is a different molecule. At most 64 molecules per call; a dataset needs at least 8 records, at least 3 per class, at most 5,000 records and at most 20 classes, with unique ids and unique SMILES. InChI, MOL/SDF blocks, protein sequences and 3D structures are not inputs.
3. **Decision boundary:** not for autonomous action on a predicted property — compound selection for synthesis without chemist review, safety or toxicity assessment, regulatory submission, clinical or exposure decisions, or any use where a wrong prediction has physical consequences — without task-specific validation on data representative of the deployment's chemistry and expert oversight. A predicted class is a hypothesis for an assay, not a measurement.
4. **Execution boundary:** not for environments where executing third-party Python is unacceptable. The loader requires `trust_remote_code=True`; pinning and digest verification narrow that boundary but do not remove it, and no security review of the upstream code has been performed beyond reading what it does architecturally.

#### Factors

###### Groups

The pipeline is not human-centric: its inputs are molecules, not people or data about people, so age, gender, skin type and socioeconomic status are not attributes of any input and no demographic evaluation applies. The factors its behaviour varies with are chemical and technical: the chemical space a molecule comes from (the pretraining corpus is drug-like PubChem and ZINC chemistry, so inorganics, organometallics, polymers, salts and very large molecules are under-represented or absent), molecular size relative to the 200-token ceiling, the presence of stereochemistry and charge annotations, and — critically — whether the SMILES is canonical, since the same molecule has many valid SMILES strings and this pipeline does not canonicalise. For the classifier, class balance and the scaffold structure of the dataset dominate: a random split of a congeneric series measures memorisation of that series. Neither the upstream authors nor this repository publishes a breakdown of the pretraining corpus by chemical class, so applicability across chemical space is uneven in a way this pipeline cannot measure, and the downstream operator must stratify their own evaluation by scaffold, series and size before trusting an aggregate number. Where molecular data relates to people — patient-derived metabolomics, personal exposure data — the operator inherits the corresponding personal-data obligations; the pipeline neither detects nor supports that case.

###### Instrumentation

There is no physical sensor between the world and this model: its input is a **string**, and the instruments that matter are the software and curation pipelines that produce that string. A molecule reaches SMILES through structure drawing or registration, a toolkit's canonicalisation algorithm, and a database's standardisation rules — salt stripping, tautomer and charge normalisation, stereochemistry perception, aromaticity model. Different toolkits and different database conventions produce different SMILES for the same compound, and this pipeline treats them as different inputs, because it performs **no canonicalisation, no standardisation, no desalting and no tautomer handling**. The labels are the second instrument: whether a property comes from an assay with its own protocol and error bars, from a computed descriptor, or from a curated literature annotation, that provenance and its error rate pass directly into the fine-tuned head, and assay-to-assay variability is a well-known ceiling on molecular property models. At inference the pipeline passes the caller's SMILES verbatim and detects only the shape errors it validates — character set, bracket balance, ring-digit pairing, token ceiling, duplicate ids and SMILES — none of which is a chemistry check.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0`, `torchvision==0.29.0`, `torchaudio==2.11.0`, **`transformers==5.17.0`** (not DIMER's standard 4.57.6 — the pinned upstream code requires an API added in Transformers 5.5.0), `huggingface-hub==1.32.0`, `tokenizers==0.23.2`, `safetensors==0.8.0`, `numpy==2.5.3` (`pyproject.toml`); the loader maps to CPU and moves the model to `device`, which defaults to `cuda:0` when CUDA is visible. Only float32 is exercised. Verified locally in a dedicated virtual environment on `torch 2.14.0+cpu`; the recorded CPU run is under "Runtime" (snapshot verification 0.1 s, load 4.6 s, 4-epoch adaptation on 36 molecules 2.0 s, whole workflow 7.5 s). Memory and time scale with tokens per molecule times batch size; the ceilings allow 64 molecules of 200 tokens, which was not measured. **Determinism is a runtime setting here, not a given:** with upstream's `deterministic_eval: false` the same molecule embeds differently on consecutive calls; this package sets it to `True`. Data environment: the model assumes SMILES of drug-like organic molecules resembling PubChem and ZINC. Its representations degrade, without any error, outside that space, on non-canonical or non-standardised strings, and on molecules near or past the token ceiling. For the classifier the load-bearing assumption is that evaluation molecules are not analogues of the training ones; if they are, the reported metrics measure scaffold memorisation, and the pipeline cannot detect this for the operator.

#### Metrics

###### Performance Measures

The pipeline reports, exactly as `metrics.classification_metrics` names them: `accuracy` (share of molecules whose argmax class is correct), `macro_f1` (unweighted mean of per-class F1 over classes present in the split), `per_class` precision/recall/F1 with `support` and `predicted` counts, and `auroc` (area under the ROC curve; binary positive class is the last entry of the class list, multiclass is the macro one-vs-rest average, computed from the Mann-Whitney rank statistic with average ranks for ties). Molecular-property datasets are routinely imbalanced — actives are rare — so accuracy alone is the wrong headline: macro-F1 and the per-class rows expose a model that has learned to answer "inactive", and AUROC measures ranking quality independently of the argmax threshold, which is what virtual-screening triage actually uses. Two baselines are reported with the same fields: `majority_baseline` (predict the most frequent training class) and `formula_baseline` (look up the molecule's **molecular formula** among training formulas and predict that formula's majority class, falling back to the training majority for unseen formulas). The formula baseline is the chemically meaningful control: composition is what a property model must beat to have learned anything about structure. The embedding stage reports **no** performance measure: it emits a 768-dimensional representation with no label, and a downstream labelled task is what gives it meaning. The executed CPU run under "Runtime" is sample-sanity evidence on synthetic molecules, not a benchmark; **no upstream benchmark number — MoleculeNet or otherwise — is reproduced or claimed in this repository.**

###### Decision thresholds

The default decision rule for `classify` is an `argmax` over `softmax(logits)` — an implicit threshold, and the only one the pipeline applies. No tuned operating point ships: the full per-class score dictionary is returned alongside the argmax label so a deployment can apply its own rule, and calibrating that rule is the operator's job. In a screening context the asymmetry is usually stark — a false negative discards a compound forever while a false positive costs one assay well — which argues for a permissive threshold on the active class plus chemist review of the borderline band; for a model whose output populates a registration field, a high threshold plus an explicit "unassigned" outcome is safer. The limits that *were* fixed during development are input-contract limits, not decision thresholds: `MAX_TOKENS = 200` (refusal, not truncation), `MAX_MOLECULES_PER_CALL = 64`, at least 8 dataset records and 3 per class, at most 5,000 records and 20 classes. No accuracy acceptance threshold was set, because this repository ships no task for which one would be meaningful.

###### Approaches to uncertainty and variability

Reported metrics come from a **single seeded holdout**: `split_dataset` stratifies by class with an explicit seed (default 42) into train/validation/test, and `evaluate` scores one split once. No cross-validation, bootstrap or repeated-run averaging is performed, and no dispersion is reported — with a 16-molecule tutorial test split, any interval would be dominated by the split. A caller who needs one repeats the workflow over seeds, or supplies enough labelled data for k-fold with scaffold-aware folds, and owns that design. Sources of run-to-run variability: the sample generator and the split are seeded; training shuffling and head initialisation are seeded through `random.seed` and `torch.manual_seed`/`torch.cuda.manual_seed_all`; non-deterministic GPU kernel selection and float accumulation order are **not** seed-controlled. The one that is specific to this model: MoLFormer's linear attention draws random feature maps, and upstream's default redraws them on every forward pass, making inference itself stochastic — this package sets `deterministic_eval=True` so that repeated calls agree exactly, and the tutorial asserts that a second embedding call returns the identical vector. During `adapt` the model is in training mode, where the features **are** redrawn each step (upstream's intended stochastic regularisation); that is why the exported adapter carries the 12 feature buffers, without which a reloaded adapter would not reproduce the adapted model — measured before the fix: a maximum absolute score difference of 0.0023, versus 0.0 after it. The per-class scores are softmax outputs of a head trained on a few dozen molecules; they are **not calibrated probabilities**, and a caller who needs calibrated confidence must fit a calibrator on held-out labelled data. Embeddings carry no uncertainty estimate of any kind.

#### Ethical considerations and biases

###### Data

Upstream discloses the pretraining data as molecules from PubChem and ZINC — public chemical databases — with this checkpoint trained on a 10 % sample of both; the upstream card does not publish a per-source, per-chemical-class or per-provenance breakdown, and that is where disclosure ends. Public molecular databases are not free of sensitivity concerns: they aggregate structures deposited by academia and industry, some from patents and publications with their own reuse terms, and a molecule can itself be commercially sensitive intellectual property. Whether any specific entry in the pretraining mix carries such an encumbrance is not established either way by the upstream authors — unknown, not ruled out. Molecular structures are not personal data in themselves, though they become linked to people in metabolomics, exposure and patient-derived contexts. This repository distributes code, tests and documentation; it does **not** vendor the weights or the upstream Python in Git (`weights/**/*.safetensors` and `weights/**/*.py` are git-ignored and reproduced from the pinned revision by `stage_missing_files`), and it ships no molecule dataset — the tutorial data is generated in code from a seeded rule and contains no compound from any database. The operator owns the audit of whatever they submit: unpublished structures are often the most commercially sensitive data a chemistry organisation holds, third-party libraries carry licence terms, and some structures are export-controlled or scheduled. Inference is local and transmits nothing, which bounds exposure but discharges none of those obligations — and the hosted-runtime warning in the tutorial exists because pasting a proprietary structure into a cloud notebook is the realistic failure mode.

###### Human Life

This pipeline is not intended for decisions in health, safety, criminal justice, employment, credit, or housing, and it has not been validated or certified for any of them by anyone. No experimental validation, no regulatory clearance, no external review board and no testing with any specific group has taken place; the only evidence in this repository is the offline unit suite (44 tests) and one executed CPU run on synthetic molecules. Use in a sensitive domain is nevertheless foreseeable — molecular property models feed drug-discovery triage, toxicity screening and materials selection — and would be admissible only with task-specific validation on chemistry representative of the deployment, scaffold-aware evaluation, a chemist reviewing every consequential output, experimental confirmation before any physical action, and whatever regulatory clearance the domain requires. A predicted property from this pipeline is a hypothesis to test at the bench, never a safety assessment.

###### Mitigations

1. **Supply-chain integrity:** `MODEL_ID` and the 40-hex `MODEL_REVISION` are module constants; `verify_snapshot()` checks `modelId`, `revision`, and the byte size and SHA-256 of all 7 manifest entries before any load and raises on the first mismatch (tests flip a digit, change the revision and delete a file and assert each raises). `stage_missing_files()` fetches only manifest-listed files absent on disk, only at `MODEL_REVISION`, only when `allow_download=True`, and refuses a manifest naming another model. `.gitattributes` carries `weights/** -text` so a Windows checkout cannot corrupt a digest through line-ending conversion.
2. **The executed Python is inside the verified perimeter:** `configuration_molformer.py` and `modeling_molformer.py` are manifest entries, and `verify_snapshot` **refuses outright** if a manifest omits them (a dedicated test drives that refusal), so the code `trust_remote_code=True` imports is digest-verified first and an upstream change fails loudly. `tools/validate_release_assets.py` additionally enforces that `trust_remote_code=True` appears **only** in the carried module cell, never elsewhere in the notebook, and that verification precedes the model-library import.
3. **The tokenizer needs no remote code:** it is a native `PreTrainedTokenizerFast` loaded with `trust_remote_code=False`, so half the load path is outside the trust boundary entirely.
4. **Determinism:** the package overrides upstream's `deterministic_eval: false`, so repeated inference on the same molecule returns the same answer, and the adapter artifact carries the linear-attention feature buffers as declared serving state so a reloaded adapter reproduces the adapted model exactly (verified: maximum absolute score difference 0.0).
5. **Artifact integrity:** the adapter is safetensors, not a pickle, and `load_artifact` checks the artifact format, the recorded base model id and revision, the class list, and the size and SHA-256 of every listed file **before** deserialising, then refuses any tensor name the base architecture does not have.
6. **Input integrity:** `embed`, `classify` and `validate_inputs` route through one checker, so their acceptance criteria cannot diverge; it rejects non-string input, empty or whitespace-padded SMILES, characters outside the accepted set, unbalanced parentheses and brackets, unpaired ring-closure digits, molecules past the token ceiling, too many molecules, and id lists that are the wrong length or not unique. `validate_dataset` additionally rejects missing columns, duplicate ids, duplicate SMILES, fewer than 2 or more than 20 classes, and any class with fewer than 3 records, and reports how many molecular formulas are shared across classes.
7. **Import boundary:** verification and validation run before `torch`, `transformers` or `safetensors` are imported (DIMER RTM-001); `tests/test_import_boundary.py` fails if a rejected request reaches a model library.
8. **Statistical mitigations:** `split_dataset` stratifies by class; no preprocessing state is fitted (the tokenizer is fixed and pinned); validation metrics are monitoring only and the final epoch is kept rather than the best; two trivial baselines are computed on the same split so a number always has a floor.
9. **Honest scope:** SMILES validation is labelled syntactic in the code, the schema, the dataset manifest and the tutorial, so no reader can mistake it for chemical validation.

Not implemented, and therefore not claimed: no security review of the upstream Python beyond reading its architecture, no sandboxing of its execution, no canonicalisation or standardisation of input SMILES, no scaffold-aware splitting, and no applicability-domain estimate.

###### Risks and harms

1. **Executing third-party code:** the default load path runs upstream Python in the operator's environment. Pinning and digest verification mean it cannot change undetected; they do not make it safe. The operator bears the risk, and it is why this profile is not yet DIMER-qualified.
2. **Scaffold leakage inflating every metric:** a random split of a congeneric series puts analogues on both sides, turning memorisation into apparent generalisation. Likelihood is high for any dataset assembled from one project's compounds, and neither the model nor this repository can detect it.
3. **Syntactic validation mistaken for chemical validation:** a string can pass every check here and still be an impossible molecule; the pipeline will embed it and return a confident-looking score. Harm ranges from a wasted computation to a nominated compound that cannot be made.
4. **Non-canonical SMILES treated as different molecules:** the same compound written two ways produces two different embeddings. An operator who mixes sources without canonicalising gets silent inconsistency in both training and inference.
5. **Out-of-distribution chemistry with no signal:** inorganics, organometallics, polymers and unusually large molecules are outside the pretraining distribution, and nothing in the output says so.
6. **Uncalibrated scores read as probabilities:** a softmax score of 0.86 from a head trained on a few dozen molecules is a ranking, not an 86 % chance of activity. A triage pipeline that treats it as a probability will mis-state its own hit rate.
7. **Proprietary structures in a hosted runtime:** the realistic confidentiality failure is a chemist pasting an unpublished structure into a cloud notebook. Inference is local, but the runtime may not be the operator's.
8. **Dual use:** a property classifier is direction-agnostic. The same model that ranks compounds for a desirable property ranks them for an undesirable one, which is why the prohibited-use section below is not boilerplate.

###### Use cases

The model must not be used to design, optimise, screen or triage compounds for chemical weapons, toxins, novel psychoactive substances intended to evade control, or any substance intended to cause harm — including inverting a property model to search for toxicity or lethality — nor to circumvent regulatory scheduling or export controls. It must not be used to produce safety, toxicity or environmental-hazard assessments presented as validated, nor to support a regulatory submission, without experimental validation and expert review. It must not be used to infer personal characteristics — health status, exposure, disease risk — about identifiable people from molecular data, nor to process structures the operator has no right to process, including third-party proprietary or patent-encumbered libraries. It must not be used to generate model-predicted properties deposited into public chemical databases without marking them as predictions, which would pollute the corpora future models train on. And it must not be used in any way that breaches the Apache-2.0 terms of the upstream weights or the DIMER deployment terms. These prohibitions hold even where the model would produce an accurate answer.

## Input/output contract

- `MolformerPipeline.from_pretrained(device=None, weights_dir=None, allow_download=False)`: stages and verifies the snapshot (refusing a manifest without the two Python files), then loads the tokenizer with `trust_remote_code=False` and the model with `trust_remote_code=True` and `deterministic_eval=True`, `local_files_only=True`; `device` defaults to `cuda:0` when visible, else `cpu`.
- `embed(molecules, *, names=None) -> dict` with `ids`, `embeddings` (one 768-float vector per molecule), `dimension`, `pooling`, `unit`, `tokens`, `n_molecules`, `model_id`, `model_revision`.
- `token_count(smiles) -> int`: tokenized length including `<bos>`/`<eos>`; the ceiling applies to tokens, not characters.
- `adapt(train_records, val_records=None, *, classes=None, epochs=4, learning_rate=1e-4, batch_size=8, trainable_layers=2, weight_decay=0.01, seed=42) -> dict`: bounded AdamW fine-tuning; returns the method description, class list, hyperparameters, trainable/total parameter counts, trainable parameter names, split sizes, the selection rule and the per-epoch history.
- `evaluate(records) -> dict`: `n`, `accuracy`, `macro_f1`, `per_class`, `classes`, `decision_rule`, `auroc`, `auroc_definition`.
- `classify(molecules, *, names=None) -> dict` with `predictions` (each `{id, smiles, tokens, label, score, scores}`), `classes`, `decision_rule`, `n_molecules`, `model_id`, `model_revision`, `adaptation`.
- `save_artifact(output_dir, metadata=None) -> Path` writes `adapter.safetensors` + `manifest.json` (format, base model id/revision/licence, `requires_remote_code`, `deterministic_eval`, class order, tensor names, **`serving_state_tensors`** naming the 12 linear-attention feature buffers, file size and SHA-256, adaptation record); `from_artifact(...)` / `load_artifact(...)` verify all of that before deserialising.
- `validate_inputs(molecules, *, names=None, token_counter=None)` and `validate_dataset(records, *, classes=None, ...)` return the input and dataset manifests; both raise exactly what the execution path would raise. `check_smiles_syntax(smiles)` returns the findings list used by both.

## DIMER deployment notes

| Field | Status |
|---|---|
| **DIMER status** | **Planned / conditional** — one gate open: the remote-code requirement |
| Licence | Apache-2.0 — use, modification, redistribution and commercial use permitted with licence and notices preserved |
| Weights | Would be redistributed unmodified; this repository redistributes none and stages them from the pinned revision |
| Remote code | **Required** — `trust_remote_code=True`; the two Python files are manifest entries and digest-verified before import |
| Runtime pin | `transformers==5.17.0` (not DIMER's standard 4.57.6); a DIMER runtime for this model needs the newer Transformers |
| Upload format | `model.safetensors` (187,248,784 bytes), plus the tokenizer files **and** the two Python files the loader executes |

**The open gate.** Under MODEL_ASSET_SPEC §12 a model that requires unresolved remote code is not ordinarily qualified (RC6), and that is the case here. What is *not* the case is RC2's failure mode — remote code enabled merely because loading failed otherwise: `AutoModel.from_pretrained(..., trust_remote_code=False)` refuses this checkpoint with a `ValueError` naming the custom code, and reading `modeling_molformer.py` shows why (linear attention with random feature maps, implemented nowhere in Transformers). The requirement is architectural. This repository narrows the boundary as far as it can — pinned revision, manifest entries, digest verification before import, a validator rule that keeps `trust_remote_code=True` out of every cell except the carried module — and leaves the qualification decision where it belongs. RC4 (explicit code/security review before production qualification) has **not** been satisfied: no such review has been performed here.

The same decision is pending for `nucleotide-transformer-genomics-pipeline`, which hit this gate first; the two rows should be ruled on together.
